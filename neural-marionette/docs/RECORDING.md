# 舞台录像与录屏性能

## 怎样使用

**内置录像**：连接摄像头或进入动作试播，点击「录制 25 秒」。自动切到 1280×720、目标 30 帧、4 Mbps 目标码率；可提前停止。视频保存后恢复之前的画质。如果原本已手动开启录屏优化，则继续保留该模式。视频仅包含舞台合成画面，不含页面控制面板、配乐与麦克风。

**macOS 区域录屏**：先勾选舞台工具栏下方的「录屏优化」，再按系统录屏快捷键选择舞台区域。录完取消勾选即可恢复画质。网页无法自动知道系统何时录屏，所以这一步需要手动操作。系统录屏的文件分辨率由所选区域决定，不保证是 720p；720p 指网页内部画布。

选择其中一种录制方式即可，避免同时运行两份编码。系统录屏是否包含声音取决于系统录屏工具的设置。

## 为什么会卡

实时运行已经包含摄像头取帧、MediaPipe CPU 推理、手势决策、Three.js 渲染与 Canvas 2D 合成。录像又增加捕获、颜色转换与编码。Web Worker 能减少主线程阻塞，却不会增加机器的计算资源。

旧实现即使只录 30 帧，仍在绘制 1080p / 60 帧；优先选择 VP9，并对摄像头画面逐帧应用滤镜。系统录屏同样会增加设备负担，因此只改内置编码器不能覆盖两种情况。

本次修改主要减少每秒绘制与合成的工作量：

| 部分 | 之前 | 录屏优化 |
| --- | --- | --- |
| 画布与目标渲染帧率 | 1920×1080 / 60 | 1280×720 / 30 |
| 每秒目标像素量 | 约 1.24 亿 | 约 0.28 亿，减少约 78% |
| 摄像头滤镜 | 饱和度、亮度滤镜 | 简单半透明颜色叠加 |
| 提线效果 | 均衡或高档辉光、粒子 | 减少粒子，停用模糊辉光 |
| 静态背景 | 每帧重画渐变与点阵 | 尺寸变化时缓存一次 |
| 内置编码 | 优先 VP9，8 Mbps | 优先 H.264 MP4，其次 VP8 WebM 等，4 Mbps |
| 画面捕获 | 独立定时捕获 | 合成完成后请求捕获；不支持时回退定时捕获 |

78% 是目标像素量的算术变化，不等于整机功耗或运行耗时降低 78%。动作由时间驱动，30 帧只是减少每秒显示的画面数，疾跑、跳跃与转身的动作时长没有改变。手势规则、个人样本、模型输入宽度 640 与推理目标上限 30 Hz 保持原配置；推理派发在渲染限帧判断之前执行，不随显示降帧一起锁步。

Three.js 绘制后，在同一个 JavaScript 帧内立即复制到最终画布，因此关闭了 `preserveDrawingBuffer`。这需要通过实际视频检查机器人是否仍完整显示，不能仅检查文件是否下载。

编码能力探测只表示浏览器报告支持该类型，**不能保证硬件编码或资源充足**。同步启动失败会尝试后续格式；运行中失败会清理录像轨道、恢复画质并保存已产生的片段（若有）。[MDN：isTypeSupported](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/isTypeSupported_static)

手动捕获使用 `captureStream(0)` 与 `requestFrame()`；该方法并非所有浏览器都支持，所以保留定时捕获回退。[MDN：requestFrame](https://developer.mozilla.org/en-US/docs/Web/API/CanvasCaptureMediaStreamTrack/requestFrame)

## 已验证与限制

2026-09-15 在本机独立、无头 Chrome for Testing（Metal 图形路径）进行了修改前后各两段 25 秒录像：动作试播和模拟摄像头＋真实本地模型。

- 修改前测试没有复现严重卡顿：页面约 60 帧，输出 VP9 1080p，约 750 个视频帧。
- 修改后页面约 30 帧；输出 H.264 720p，约 25 秒、750 个视频帧，解码后可见机器人与提线。
- 这些结果证明降低负担后录像可用，不能证明已复现并修复用户在内置浏览器或 macOS 区域录屏中的全部卡顿原因。

进一步的流程测试在真实模型处理模拟摄像头后注入合成 21 点，以同时覆盖推理与骨架绘制负载。测试检查完整 25 秒、实际解码帧间隔、提前停止、退出摄像头、画质恢复、手动开关保留、编码启动失败、运行中错误、VP8 与定时捕获回退以及视频轨道释放。证据见 测试结果（本地记录，未随公开版本提供），脚本为 `tests/recording_browser_test.py`。这不是真人手势验收，也没有实际操控 macOS 系统录屏。

## 如果仍然卡顿

先确认「录屏优化」已开启，只保留一种录像工具。分别观察未录屏和录屏期间的「渲染 FPS」「追踪 Hz」「帧处理」：

- FPS 明显低于 30，推理值稳定：重点检查画面合成、图形加速和录像负载。
- 追踪 Hz 下降、帧处理明显上升：可能存在 CPU 竞争、取帧或线程通信延迟，不能只看模型推理时间。
- 页面顺畅而下载的视频卡顿：重点检查编码与捕获路径，需要分析实际视频的帧时间。

可在同一次会话中先运行数秒，再开始录屏，最后点击「导出诊断」。报告现在包含每段采样的录制状态、目标 FPS、实际 FPS、追踪 Hz、画面更新耗时和录像格式。`renderMs` 是 JavaScript 调用阶段的耗时，不包含所有异步 GPU 或编码耗时；`submittedFrames` 是提交捕获次数，不等于编码文件的实际帧数。

若要对照独立 Chrome，请使用同一地址，并先导出个人手势样本；不同浏览器不共享 localStorage。不要为排查卡顿清除站点数据。
